## The Documentation Nobody Opens

Every team has that documentation folder — thorough, well-intentioned, and mostly ignored. The problem usually isn't quality. It's timing and shape.

Developers don't read docs linearly. They arrive mid-task, usually stuck, searching for one specific answer. If your docs are structured like a book instead of a reference, you've already lost them.

## Write for the Moment of Friction

Good developer documentation anticipates the exact question someone asks when something breaks or looks unfamiliar:

- **Getting started guides** should get someone to a working state in minutes, not explain every concept up front.
- **Reference docs** should be scannable — headings, code blocks, and parameters that can be found via Ctrl+F.
- **Conceptual guides** are for the 20% of readers who want the "why," and should be clearly separated from the "how."

## Show, Don't Just Tell

A code sample that runs is worth more than three paragraphs describing behavior. Whenever possible, pair prose with a minimal, copy-pasteable example — not a truncated snippet missing the imports.

## Keep Docs Close to the Code

Documentation that lives far from the codebase rots quietly. Teams that keep docs versioned alongside code, or generate them from the same source of truth, catch drift before users do.

## The Real Test

The best test for documentation isn't whether it's comprehensive — it's whether someone unfamiliar with the system can solve their problem without asking a human. That's the bar worth writing toward.
